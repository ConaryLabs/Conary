# Remi Host Rebuild

This runbook owns the reproducible rebuild boundary for the Hetzner Remi
origin. It contains no credentials. Host-local keys, tokens, recovery archives,
and access aliases remain outside the repository.

## Destructive boundary

The tracked installimage configuration erases both complete devices below:

- `/dev/nvme0n1`
- `/dev/nvme1n1`

Before invoking it, independently verify both model/serial pairs, SMART health,
the Ubuntu image path, the current recovery archives, and explicit owner
approval for those exact devices. Do not infer approval from an earlier
inspection or from the existence of this file.

The resulting storage contract is:

| Layer | Backing | Usable size | Contract |
| --- | --- | ---: | --- |
| `/boot` | 1 GiB partition on each NVMe | 1 GiB | Linux md RAID1, ext4 |
| `/` | 160 GiB partition on each NVMe | 160 GiB | Linux md RAID1, ext4 |
| swap | file on `/` | 32 GiB | mirrored by the root array |
| data md | remaining partition on each NVMe | about 1.55 TiB | Linux md RAID0 |
| VDO physical | data volume group | 1.50 TiB | compression, deduplication, thin provisioning |
| `/data` logical | VDO logical volume | 3.0 TiB | XFS |

Keep the remaining volume-group capacity unallocated. It is recovery and
metadata headroom, not spare logical filesystem capacity. `/data` is the
authoritative large-data root; `/data/work` binds to `/work` and
`/data/conary` binds to `/conary`.

RAID1 protects the bootable operating system from one device failure. RAID0
and VDO do not protect `/data` from device loss or corruption. Recovery proof
is therefore part of the storage design rather than an optional follow-up.

## Recovery gate

Before destruction, create and verify recovery archives on a separate machine.
Inspect archives in empty staging directories; never extract a recovery archive
over `/`. The minimum non-reproducible inventory is:

- Remi configuration, repository signing material, TLS material, nginx state,
  service overrides, timers, and scheduled maintenance configuration
- administrator SSH state required to regain access
- selected interactive development authentication and configuration
- any working-tree change that is not committed and available from its remote

Large package caches, build outputs, cloned repositories with clean remote
commits, test artifacts, and audit scratch are reproducible and should not be
restored wholesale.

## Rescue installation

Boot Hetzner Rescue, install an explicitly approved public SSH key, and verify
the destructive targets:

```bash
lsblk -d -o NAME,SIZE,MODEL,SERIAL,TYPE
nvme smart-log /dev/nvme0
nvme smart-log /dev/nvme1
test -f /root/.oldroot/nfs/images/Ubuntu-2604-resolute-amd64-base.tar.zst
test -x /root/.oldroot/nfs/install/installimage
```

Copy `deploy/hetzner/remi-installimage.conf` to
`/root/remi-ubuntu-2604.conf`, compare it byte-for-byte with the reviewed
source, and pass that absolute path to installimage. Hetzner's shared
`install/configs` directory is read-only; `-c` accepts an absolute local path.
Run:

```bash
/root/.oldroot/nfs/install/installimage -a -c /root/remi-ubuntu-2604.conf
```

The fixed-size partition declarations deliberately leave the tail of each disk
unused. Do not add an `all` partition to the installimage configuration.

Before rebooting, record `/proc/mdstat`, the generated partition tables,
`/etc/mdadm/mdadm.conf`, `/etc/fstab`, installed SSH keys, and the bootloader
result from the mounted target. Reboot only after all of those agree with the
reviewed layout.

## Installed-host provisioning

On the first Ubuntu boot, update packages and install the storage and service
baseline before restoring data:

```bash
sudo apt-get update
sudo apt-get full-upgrade -y
sudo apt-get install -y mdadm lvm2 vdo xfsprogs nvme-cli smartmontools \
  parted nginx certbot git build-essential clang mold pkg-config libssl-dev \
  nodejs npm fd-find gh bubblewrap tmux mosh jq zstd rclone
```

Inspect the actual partition table generated by installimage before creating
the remaining partitions. `deploy/hetzner/remi-provision-data.sh --plan`
validates both parent-device serials, mounted RAID1 authority, equal unused
tails, and absence of prior data-tier state. Its `--apply` mode requires the
literal confirmation token printed by `--help` before it creates equal `p3`
partitions and the RAID0 array.

Use the installed versions of `lvmconfig`, `lvcreate`, and `vdo` as command
authority. The tracked data-tier procedure must explicitly set and verify:

- 4 KiB minimum VDO I/O size
- dense 1 GiB VDO index
- 1 GiB block-map cache
- compression enabled
- deduplication enabled
- 1.50 TiB physical allocation
- 3.0 TiB logical allocation
- XFS creation without an initial discard across the full logical range

Do not create the VDO volume from remembered syntax. Confirm the installed
LVM/VDO profile keys first; `deploy/hetzner/remi-vdo.profile` preserves the
accepted settings. VDO physical usage is the exhaustion authority; `df` only
reports logical XFS usage. The provisioner installs and enables the tracked
five-minute physical-capacity monitor before restored or generated data enters
the volume.

Create a 32 GiB root swapfile, mount `/data`, create `/data/work` and
`/data/conary`, then add the XFS mount and both bind mounts to `/etc/fstab` by
stable identifiers. `findmnt --verify --verbose` must pass before reboot.

## Identity contract

The rebuilt host has three human/service boundaries:

- `peter`: administrator with key-only SSH and passwordless sudo
- `dev`: the sole interactive development account
- `conary`: non-login service account for Remi and production-owned paths
- `conary-web`: traversal-only system group containing `conary` and Ubuntu's
  `www-data`; `/conary` remains mode 0750 with this group while sensitive
  children retain their stricter `conary:conary` modes

Do not recreate `conary-dev` or `signed-dev`. Merge reviewed configuration into
`dev` selectively. Keep production repository state, signing material, static
sites, releases, and service runtime state owned by `conary:conary`; development
checkouts and caches are owned by `dev:dev`.

Install `deploy/hetzner/remi-dev-session.sh` as `dev`'s `~/.local/bin/dev`.
It owns the single-account tmux entrypoints for the clean Conary, Nomos, and
The Mortal Estate checkouts; do not recreate project-specific login users
merely to recover their old session names.

Enable `deploy/systemd/codex-app-server-bootstrap.service` in `dev`'s lingering
user manager after Codex authentication. Its boot-time upstream bootstrap is
the authority for restoring the pid-backed app-server, updater, and Remote
connection after a host reboot.

Disable password SSH authentication and direct root SSH after verifying a fresh
`peter` login and `sudo -n true`. Verify `dev` through a fresh login rather than
only through `sudo -u dev`.

## Selective restore and service recovery

Clone clean repositories from their remotes, verify expected commit IDs, and
then restore only reviewed non-reproducible state. Extract each archive into its
own empty inspection directory and install individual paths with explicit
owners and modes. Never use an archive as filesystem authority.

Restore and verify, in order:

1. repository signing authority and Remi configuration
2. Remi database/state required for the intended repository epoch
3. certificates and renewal hooks, followed by the tracked Ubuntu nginx map
   and origin vhost in `deploy/nginx/`
4. tracked systemd units and the root-owned deploy helper/sudo policy
5. development authentication/configuration selected for `dev`
6. current unpinned developer tools and the repository-owned Rust toolchain

Restart nginx after adding `www-data` to `conary-web` so its workers acquire
the supplementary group. Verify the worker's effective groups and prove both
the public site and branded 404 response; a successful `nginx -t` does not
prove filesystem traversal.

## Completion proof

The rebuild is incomplete until a disk boot, a second reboot, and all of the
following evidence have been recorded in the issue-linked pull request:

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
cat /proc/mdstat
sudo mdadm --detail /dev/md0
sudo mdadm --detail /dev/md1
sudo mdadm --detail /dev/md2
sudo pvs
sudo vgs
sudo lvs -a -o+devices,data_percent,metadata_percent,vdo_compression,vdo_deduplication
findmnt --verify --verbose
systemctl --failed
systemctl status remi nginx
scripts/remi-health.sh --full
sudo /usr/local/sbin/conary-remi-deploy inspect-remi --require-repopulated
```

Also verify fresh administrator and development SSH sessions, certificate
renewal simulation, public HTTPS endpoints, timers, VDO monitoring, SMART
health, RAID membership, and fresh local plus off-host recovery artifacts. A
known product defect remains a failed completion item with its issue linked;
it does not become green through repeated retries.
